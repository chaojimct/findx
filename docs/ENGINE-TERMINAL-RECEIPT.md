## Exact handoff
Elevated local Windows pipe clients use CheckpointIdentity(protocol2), PrepareStop(version2, expected instance, unique nonce, exact canonical index, deadline), then exact StopToken CommitStop or CancelStop. Missing fields never default. Protocol1 negotiation remains negative; legacy2.5.2 cannot implement this protocol and must be refused before STOP. Search/Unix direct dispatch cannot call these operations. Per-frame named-pipe impersonation checks an enabled built-in Administrators SID, on a dedicated short-lived OS thread (no token leaks into Tokio). Anonymous/filtered/unverified clients are denied. No client-supplied PID/auth/environment override. Caller must still independently verify owned SCM service/PID/executable/index; admin authentication is NOT a claim to have evaluated arbitrary custom SCM object ACLs.

The existing Prepare actor closes and drains ALL registered work, then actual freeze commits the sealed namespace using the real writer and reads its published generation. StopToken binds protocol2, OS-random engine instance, PID, request nonce, canonical index identity, RAM mutation sequence, runtime outcome epoch and actual writer/pointer generation. Metadata-incomplete snapshots cannot commit even if a privileged caller guesses every other field.

Commit equality and runtime outcome validation occur under the same Work mutex as producer error/final-permit publication. The actual FrozenCheckpoint (namespace+admission+publication guards) stays in the actor; it is NOT dropped/re-frozen/re-saved on committed STOP. Receipt bytes are create-new temporary file + sync_all + existing atomic WRITE_THROUGH replace, then deadline recheck. IO/deadline failures produce no commit response, retain RAM, release preparation and force later full resync via existing dirty bookkeeping. A timed-out/orphan receipt without matching live-instance exact commit response is not valid installer authority. The final token filename is instance+validated nonce-specific; no caller-controlled arbitrary path.

Commit response and file both describe saved_stop_pending, process_stopped=false. They do not assert SCM0/stopped. Exact repeated commit is idempotent only in the same still-committed actor. A committed cancel is rejected and the RAM stays sealed in an explicit safe state until normal SCM STOP; there is no forced cancellation/termination of blocking IO. A precommit cancel or expiry reopens admission, cannot replay its consumed nonce, and late/wrong instance/request/index/sequence/generation/epoch cannot sign. Raw STOP without a committed token follows the prior save/retry path with NO new receipt. Stop consumes the retained committed frame only after actual worker shutdown and outcome validation; ordinary final save is skipped, avoiding a deadlock/resave that would reopen/change the acknowledged generation.
