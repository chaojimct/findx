# FindX 2.5.10 — 发版记录（本地验收）

GitHub Release 构件由 `release.yml` 在 tag `v2.5.10` 上的 CI 重建（仅 Windows）产生；
本地验收结论（`release/2.5.10.json` 的门）：

## 门 1：engine-io-storm-fixed（P0，通过）

- 现象（发版前）：findx2-service 常态 ~300MB/s 磁盘写入，任务管理器 I/O 列持续标红。
- 根因（三层，均已实锤）：
  1. 每提交全量拷贝段文件（names 622MB + entries 316MB + trigram 334MB…≈1GB），NTFS 不实现
     `FSCTL_DUPLICATE_EXTENTS_TO_FILE`（生产环境实测 rc=50 全勤），block-clone 路线判死刑；
  2. 同批 push+patch 被旧边界检查误判，每 ~30s 一次 NeedFull 全量快照；
  3. backfill 终态 persist 与停机 persist 绕过提交门。
- 修复：WAL（5 秒心跳 fsync，只写增量）+ fold 按 256MB/2h/100 万日志三档触发；
  提交阈值、digest 复用、停机 bound 保留为纵深。
- 证据：换版后 Task Manager 磁盘写入 1.6MB/s（原 300MB/s）；40+ 分钟零 fold；
  `service-win.log` 只有心跳级 WAL append，无 `checkpoint delta`（此前每 10-20 秒一次 1GB）。

## 门 2：wal-crash-recovery（P0，通过）

- 方法：生产库在线、`taskkill /F`（无优雅停机，等价断电）→ `sc start`。
- 结果：启动日志 `WAL seq regression (tip 79 < gen 668): replaying from 0` +
  `WAL replay: 79 frames, 872 mutations`；post-gen 标记文件可搜；无 crash 循环、无 PANIC。
- 覆盖的回归：seq 回归（retain 曾清空文件致 seq 重启）、torn tail、中段 CRC 损坏（大声失败）、
  FullResync 停播、pre-length 缺口（优雅降级游标续跑）。另有 `probe_prod_*` 系列可手动复现。

## 门 3：persist-test-suites（P0，通过）

- `cargo test -p findx2-core` 全 target 串行通过（含 WAL 8 项：roundtrip/torn-tail/retain 锚点/
  mid-file 腐坏/逐字节重播一致性/生产 WAL 回放）；
- `cargo test -p findx2-service` 77 项串行通过（含心跳/fold/失败重试/停机 20 项 run 测试）。

## 门 4：fold-quiescence-in-prod（P0，通过）

- 2.5.10（fold 门 + 原因日志）上线后观察：提交间隔从 ~30 秒拉到小时级；
  `fold due` 日志此后只应在 wal-size/journal-ram/staleness/forced 四种原因下出现。

## 门 5：legacy-2-4-multivolume-index-loads（P0，通过）

- 随全量套件通过（`legacy_multivolume_load` 三用例 + v6 roundtrip），无格式迁移。

## 未跑的门（P1/P2，非阻塞，均在 json 中标 false）

- installer-live-handoff：本次只做手动 swap（payload-manifest 已同步），未跑安装包升级；
  下次发版若走安装包需重跑。
- strict-protocol2-stop-receipt、macos-linux-native-packaging：延续 2.5.9 状态。
